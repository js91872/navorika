# Navorika Locked Content & SEO Strategy

Status: **LOCKED BASELINE**
Effective: 2026-10-09

This document defines the permanent publishing standard for Navorika. Existing tools, guides, URLs, templates, taxonomy, and SEO copy should not be routinely rewritten after this baseline.

## 1. Lock Policy

After this baseline:
- Do not rewrite existing tool pages for minor keyword variations.
- Do not change existing URLs, slugs, canonicals, category paths, or guide paths for SEO experiments.
- Do not redesign the global tool-page or guide-page layout unless there is a verified usability, accessibility, legal, security, or technical defect.
- Do not expand existing pages simply to reach a word-count target.
- Do not add speculative keyword stuffing, city/location variants, or unrelated long-tail terms to pages.
- Existing pages may be amended only for:
  - factual or calculation errors;
  - broken functionality;
  - security/privacy issues;
  - legal/compliance requirements;
  - materially outdated standards, rates, or official rules;
  - indexing/canonical/schema bugs;
  - clear evidence of harmful keyword cannibalization.
- Growth work should focus on **new tools, new guides, new clusters, and external authority**, not repeated rewrites.

## 2. Navorika Positioning

Navorika is a **tool-first, task-first utility platform**.

Primary value proposition:
- useful tools that solve a specific task quickly;
- plain-language explanations;
- transparent formulas and assumptions;
- privacy-first local processing where possible;
- no signup for ordinary use;
- honest capability limits.

Articles and guides support tools. They are not the primary product.

## 3. New Tool Selection Rule

A new tool should normally satisfy all of the following:
1. Clear standalone search intent.
2. The task is not already solved adequately by an existing Navorika URL.
3. Search demand is measurable through current keyword research or emerging Search Console data.
4. The calculation/conversion can be implemented accurately and explained transparently.
5. The tool belongs naturally in an existing category or a justified new cluster.
6. The page can link to at least 2-3 useful related tools or guides.
7. The tool has long-term evergreen value unless an intentionally time-sensitive opportunity is approved.

Prefer:
- lower SEO difficulty;
- high intent-to-tool fit;
- problems with a direct input -> result workflow;
- topics where Navorika already has topical adjacency;
- Tier-1 country search demand where appropriate.

Avoid:
- near-duplicate calculators;
- fake converters that cannot produce the claimed output;
- tools requiring unavailable proprietary formats or data;
- thin keyword variants;
- search terms whose intent is mainly brand, software download, piracy, or another unrelated product.

## 4. Frozen Tool Page Template

Every new tool should follow this structure.

### Above the fold
1. Short intent label/eyebrow.
2. Exact, natural H1 matching the main user task.
3. One short description explaining what the user can calculate/convert/check.
4. Tool interface immediately visible.
5. Result area close to the inputs.
6. Privacy/data handling statement when relevant.

### Supporting content
Use the shared ToolPageContent pattern:
1. Suggested next steps / workflow links.
2. What is [Tool Name]?
3. How [Tool Name] works.
4. How to use [Tool Name].
5. What the result means.
6. Important limitations.
7. Explore this topic / toolkit where relevant.
8. Frequently asked questions.
9. Related tools.
10. Related guides.

Do not invent extra sections unless the subject genuinely needs them.

## 5. Tool Copy Standard

Write for a normal user first.

Preferred language:
- "Calculate how many bricks you need."
- "Enter the room length and width."
- "See the estimated cost per linear foot."
- "Convert a PDF page to JPG."

Avoid unnecessary internal or engineering language above the fold:
- "matrix editor";
- "pharmacokinetic elimination model";
- "geometric dictionary inspection";
- "raster processing pipeline".

Technical terms are allowed in lower sections where they help accuracy.

### Title/H1 rules
- Put the main search task early.
- Prefer natural phrases users type.
- Keep the title descriptive rather than promotional.
- Do not force "free", "best", or "online" into every title.
- Use "online" where it helps distinguish the task.
- Use units or output terms where they clarify intent.

### Intro rules
The first paragraph should normally answer:
- what the tool does;
- what the user enters;
- what result it returns.

Do not begin with company history, methodology philosophy, or long disclaimers.

## 6. Formula and Accuracy Standard

Every calculator must:
- use an explicit formula or deterministic calculation;
- state units;
- validate invalid/negative inputs;
- separate user assumptions from calculated outputs;
- label estimates as estimates;
- distinguish geometry/planning calculations from structural, medical, legal, tax, or professional advice.

Where standards or official rules are material, cite or name the governing standard/source in the content or methodology.

Never claim a converter produces a native/proprietary format unless it genuinely does.

## 7. SEO Standard for New Tools

For every new tool:
- one primary keyword intent;
- 4-10 closely related secondary phrases;
- no unrelated keyword expansion;
- unique title and meta description;
- canonical URL;
- WebApplication/SoftwareApplication-style tool schema through the existing SEO system;
- FAQ schema only from visible FAQ content;
- crawlable internal links;
- inclusion in the registry;
- assignment to a taxonomy cluster;
- assignment to a toolkit when naturally relevant;
- automatic sitemap inclusion through the registry.

Do not create multiple URLs for spelling, plural, "free", "online", or minor wording variants.

## 8. Internal Linking Standard

Each new tool should connect to the user workflow, not merely to random tools in the same category.

Priority order:
1. Previous/next workflow tool.
2. Same calculation family.
3. Same project/task.
4. Supporting guide.
5. Category/toolkit page.

Typical target: 3-8 meaningful internal links on a tool page through the existing components.

Avoid excessive exact-match anchor repetition.

## 9. Frozen Guide / Article Template

Guides exist to answer a real search question and lead naturally to useful tools.

### Required article structure
1. Feature image.
2. Search-first H1.
3. Short answer/introduction in approximately 40-100 words.
4. Practical steps or direct explanation.
5. Worked example where useful.
6. Main explanation sections using question/task-based H2s.
7. Common mistakes or limitations.
8. Related tool CTA in context.
9. FAQs where search intent supports them.
10. Related guides/tools at the end.

### Length
There is no mandatory word count.

Typical ranges:
- simple how-to: 900-1,500 words;
- comparison/explanation: 1,200-2,000 words;
- complex reference guide: 1,800-3,000+ words only when the topic genuinely requires it.

Never pad to 2,500 words.

## 10. Guide Language Standard

Use:
- short paragraphs;
- plain English;
- descriptive H2s;
- examples;
- tables only when they simplify comparison;
- bullets for steps, requirements, or options.

Avoid:
- AI-style introductions;
- repeated summaries;
- inflated vocabulary;
- generic "In today's digital world..." openings;
- excessive "it is important to note";
- repetitive limitations in every section;
- unnecessary declarations about the article itself.

Technical detail belongs after the simple answer.

## 11. Feature Image Standard

For guides/articles:
- 1200 x 630 preferred for social/Discover compatibility;
- original, high-quality, relevant visual;
- no text-heavy thumbnail unless text materially helps;
- strong central subject;
- clean contrast;
- avoid generic stock imagery;
- descriptive filename and useful alt text when the image itself conveys information.

For calculators, feature images are generally unnecessary unless the page is also promoted as editorial content.

## 12. Schema Standard

Use schema that matches visible content:
- WebSite + Organization globally;
- tool/application schema for tools;
- FAQ only when FAQs are shown;
- Article/BlogPosting for guides;
- BreadcrumbList through the shared breadcrumb system;
- ItemList for directories where already implemented.

Do not add schema solely to increase schema count.

## 13. New Content Research Workflow

Before creating a new tool or guide:
1. Check the Navorika registry and existing URLs for overlap.
2. Review Search Console when available for emerging queries.
3. Use current keyword research for volume, difficulty, CPC and related phrasing.
4. Inspect the likely SERP intent.
5. Decide whether the query deserves:
   - a new tool;
   - a guide;
   - both;
   - or no page.
6. Define one canonical target URL.
7. Build the page once to the frozen standard.
8. Publish and allow search engines time to evaluate it.

Do not repeatedly rewrite a page during the first weeks because rankings are still moving.

## 14. Post-Publish Rule

After a page is published:
- verify HTTP 200;
- verify canonical;
- verify sitemap inclusion;
- verify title/H1;
- test calculator/converter output;
- check mobile usability;
- check internal links;
- verify no accidental noindex.

Then leave the page alone.

Performance should normally be evaluated after enough impressions accumulate. Prefer adding new supporting content or links over rewriting the page unless data shows a specific problem.

## 15. Growth Priorities After Lock

Priority 1: New low/medium-difficulty tools with strong task intent.
Priority 2: Guides supporting tools already receiving impressions.
Priority 3: Better external authority/backlinks and genuine mentions.
Priority 4: Distribution through search, Discover, communities, and useful references.
Priority 5: Only then consider major legacy-page changes based on evidence.

## 16. What Is Frozen

The following are considered stable defaults:
- URL architecture;
- seven main categories;
- tool-first page layout;
- guide-card/list layout;
- shared SEO tool content structure;
- privacy-first positioning;
- plain-English search-first writing style;
- registry-driven sitemap;
- cluster/toolkit internal-linking model;
- existing pages as of this baseline.

Future work should extend this system, not repeatedly redesign it.

## 17. Exception Rule

If an existing page must be changed after lock, the commit or task should clearly state one of these reasons:
- BUG
- SECURITY
- LEGAL
- FACTUAL CORRECTION
- STANDARD/RATE UPDATE
- INDEXING FIX
- CANNIBALIZATION FIX

"SEO improvement", "make richer", "add more words", or "try new keywords" is not enough reason by itself.

---
Navorika should now grow mainly by publishing **new useful tools and genuinely useful supporting content**, while allowing the existing indexed footprint to age, gain trust, links, impressions and rankings.
